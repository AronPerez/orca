Orca Mobile over-the-air update infrastructure

A plan to ship React Native UI polish and JavaScript bug fixes without waiting for an App Store or Play Store review, while keeping native changes on the normal store release path.

Recommended: self-host Client: expo-updates Infrastructure: GCP + CDN Signing: Cloud KMS
✓

Recommended decision

Use the open-source expo-updates client and Expo Updates Protocol, but operate the manifest service, release storage, signing, approvals, and rollout state on Orca infrastructure. Keep a human approval before production promotion and automate preview releases.

01 · Outcome

What this changes

The store version becomes a native runtime shell plus a known-good embedded bundle. Most application behavior remains TypeScript and JavaScript, and compatible bundles can be delivered independently after the shell has passed store review.

Primary benefit

Minutes instead of store-review days

Source-control UI polish, terminal rendering changes, interaction fixes, copy, styling, state management, and compatible transport fixes can ship through OTA.

Continuing constraint

Native releases still exist

New native modules, permissions, entitlements, Expo or React Native upgrades, and changes to the custom audio implementation still require store binaries.

This is not a mechanism for bypassing store policy. OTA should be used for code compatible with the reviewed native runtime. Material changes to the app's purpose or native capabilities stay on the store path even if they are technically expressible in JavaScript.

03 · OTA boundaries

What can and cannot ship over the air

Change OTA? Notes
Source-control layout, interactions, and styling Yes React Native TS/TSX within the existing runtime.
Terminal rendering, xterm configuration, and WebView-injected code Usually Safe while relying only on WebView/native APIs present in the target runtime.
Navigation, state, transport, RPC, and business-logic fixes Usually Desktop/server protocol compatibility must include older mobile runtimes.
Pure JavaScript dependency update Usually Only when Metro bundles it and it introduces no native code or configuration.
New native package or Expo config plugin No The native binary must contain the module before JavaScript can call it.
Expo SDK, React Native, or native dependency upgrade No Create a new runtime version and submit new binaries.
Audio engine Kotlin, Swift, or Objective-C change No The custom native module is compiled into the app binary.
Permissions, entitlements, Info.plist, AndroidManifest, icon, or splash No These are native package and store-review concerns.
Material change to the app's primary purpose Store path Keep product-policy review separate from technical OTA capability.
Compatibility rule: an update may only target a runtime version whose native modules and configuration satisfy every API used by that bundle. When native compatibility changes, increment the runtime version and ship through the stores.

04 · User experience

How updates feel to a user

  1. The app always has a launchable bundle

    A store install contains an embedded bundle. Later launches use the newest compatible verified bundle already cached on the device.

  2. Update checks happen quietly

    On launch or resume, the app asks for an update matching its platform, runtime version, and release channel. Routine checks should not block startup.

  3. The bundle downloads in the background

    The client verifies the signed manifest and asset hashes before making the release eligible. Invalid or incomplete updates are rejected.

  4. The update applies at a safe boundary

    Default behavior should apply routine releases on the next cold launch. For an important fix, show a concise “Update ready — Restart” action after download.

  5. Failure falls back instead of blocking use

    Network or service failure leaves the current bundle running. A bad release can be rolled back by repointing production to a previously signed manifest.

Users see no App Store prompt for an OTA release. Store updates remain visible only when Orca ships a new native runtime or changes store-managed capabilities.

05 · Architecture

Small control plane, static delivery plane

Use Expo's client and public protocol while keeping the operational surface narrow. Releases are immutable; only channel pointers change.

Native shell

Installed through the stores

Contains React Native, Expo modules, custom native modules, an embedded fallback bundle, update URL, runtime identifier, and OTA public certificate.

Manifest service

Cloud Run

Selects a signed manifest using platform, runtime version, and channel. It should not sign dynamically or rewrite immutable release content.

Release storage

GCS behind a CDN

Stores content-addressed bundles, assets, and signed manifests with long immutable cache lifetimes. Bandwidth is the main variable infrastructure cost.

Release state

Firestore channel pointers

A small mutable record maps channel, platform, and runtime to a release. Pointer changes support promotion and instant rollback without rebuilding.

Signing

Google Cloud KMS

Holds a non-exportable, dedicated OTA RSA key. CI submits a SHA-256 digest and receives the detached RSA PKCS#1 v1.5 signature required by Expo.

Compatibility

Explicit runtime versions

Every native compatibility set gets an identifier. Multiple store versions may remain active, each receiving only compatible updates.

06 · Signing and approval

Protect the update path independently of desktop signing

Signing proves that a manifest was authorized by Orca. The signed manifest contains cryptographic hashes for the JavaScript bundle and assets, so the signature extends transitively to everything the client installs. HTTPS still protects transport, but signature verification protects against storage, CDN, routing, or credential compromise serving unauthorized code.

Concern Desktop Windows Mobile OTA
Trust root Public CA and Windows Authenticode trust Public certificate embedded in the Orca mobile binary
Provider SignPath OSS program Google Cloud KMS recommended
Key SignPath-controlled Windows code-signing key Dedicated, non-exportable OTA RSA key
Approval Required by the SignPath OSS policy Orca-controlled production promotion policy
Frequency One approval per desktop release signing request One approval and signature per unique production manifest, not per client
Why not reuse SignPath OSS? SignPath's published product matrix places arbitrary hash signing under Code Signing Gateway. The OSS program's key and forced approval workflow are designed for supported code-signing artifacts, and the private key is not exportable. Orca can ask SignPath about an exception, but should not depend on one.

Recommended production approval flow

  1. CI builds and tests an immutable release candidate.
  2. A protected deployment environment creates an approval request.
  3. The existing release bot posts the candidate and approval link in Slack.
  4. An authorized team member approves or rejects production promotion.
  5. After approval, a narrowly scoped CI identity asks KMS to sign the manifest.
  6. CI uploads immutable content and atomically advances the production pointer.

Preview policy

Automatic

Protected branches may publish to an internal channel without human approval.

Production policy

One human approval

Preserve the familiar Slack workflow without making approval a permanent property of the cryptographic provider.

Key rotation normally requires a store release that embeds the next public certificate. Plan rotation before expiry or suspected compromise, and keep KMS signing permission isolated from the manifest-serving runtime.

Self-hosted versus Expo-hosted

Upfront implementation effort is intentionally excluded from this decision. The table focuses on steady-state cost, maintenance, and control.

Pricing clarification: 5,000 users downloading ten releases in one month are approximately 5,000 update MAUs, not 50,000 MAUs. They do create 50,000 downloads and therefore use the corresponding bandwidth. Verify Expo's current plan terms before making a purchasing decision.

Why self-host wins here

Orca already operates GCP services, has credits, and has Cloudflare available. The delivery plane is mostly static, signing volume is tiny, and service downtime delays updates rather than preventing app launch.

When to choose EAS instead

Choose EAS if no one can own release infrastructure, if 2–6 monthly maintenance hours cost more than the control gained, or if managed rollouts and analytics become operationally important.

Managed features intentionally deferred

Self-hosting does not reproduce every EAS product feature. These are useful, but Orca does not need them to solve the current shipping-velocity problem.

EAS feature Initial Orca substitute Why that is sufficient
Hosted release dashboard CI run, release record, and a small internal status view Release operators need auditability, not a broad product dashboard.
Managed branches and channels Firestore pointers for internal, production, and optional canary Orca needs a small fixed channel set rather than arbitrary branch topology.
Percentage rollouts Internal dogfood, then full promotion with instant rollback Add deterministic cohorts only after release volume justifies them.
Republish and revert UI Audited CI promotion and rollback commands A pointer change is enough; a polished public control surface is unnecessary.
Managed update insights Focused client telemetry and Cloud Monitoring Adoption, launch success, fallback, and errors cover the operational decision.
Managed code signing Cloud KMS, workload identity, and Cloud Audit Logs The signing operation is infrequent and maps directly to existing GCP controls.
Managed asset hosting and retention GCS lifecycle rules plus CDN caching Assets are immutable and retention requirements are straightforward.

  • Download duration and failure class

09 · Delivery plan

Implementation phases

Complete the work behind an internal channel first. The existing store app remains unaffected until the OTA-capable native shell is released.

Phase 1

Protocol and release contract

  • Define release ID, platform, runtime version, channel, and manifest schema.
  • Define which repository changes force a new native runtime.
  • Choose update check and apply behavior for foreground and cold launch.
  • Document App Store and Play policy review rules for release managers.
Phase 2

OTA-capable mobile shell

  • Add and configure expo-updates.
  • Configure the self-hosted update URL and explicit runtime version.
  • Embed the OTA public certificate and a known-good fallback bundle.
  • Add update lifecycle logging and recovery behavior.
  • Ship the new native shell through TestFlight and internal Android testing.
Phase 3

GCP release infrastructure

  • Create immutable GCS release storage and CDN configuration.
  • Create Firestore channel and release records.
  • Implement the Expo Updates Protocol manifest endpoint on Cloud Run.
  • Create the Cloud KMS signing key and certificate.
  • Prevent Cloud Run and client-facing identities from signing or promoting.
Phase 4

Publishing, approval, and rollback

  • Build one deterministic bundle and manifest per platform/runtime target.
  • Validate manifest asset hashes before submitting the signing digest.
  • Publish preview automatically from an approved branch.
  • Add protected production approval and the Slack request message.
  • Add atomic promotion and rollback commands with an audit trail.
Phase 5

Verification and controlled launch

  • Test valid, invalid, expired, truncated, and wrong-runtime manifests.
  • Test offline launch, interrupted download, failed apply, and rollback.
  • Dogfood through an internal channel across iOS and Android.
  • Release the OTA-capable shell through both stores.
  • Start production with a small cohort before enabling the full channel.

10 · Acceptance criteria

Conditions for production readiness

  • A UI-only source-control change reaches an internal device without a store build.
  • A terminal rendering fix reaches both platforms under the correct runtime version.
  • An update signed by an unknown key is rejected and the previous bundle launches.
  • A manifest with a modified bundle or asset hash is rejected.
  • An update requiring an unavailable native module is never offered to that runtime.
  • Production cannot advance without the configured human approval.
  • Slack identifies the release, commit, runtime, channel, and approval destination.
  • A production rollback completes by pointer change without a new bundle or signature.
  • An update-service outage does not prevent cold launch of the cached or embedded app.
  • Operators can see update adoption, launch success, and failures by release ID.

11 · Open decisions

Resolve before implementation

Decision Recommendation Reason
Runtime version format Explicit native compatibility identifier JavaScript-only releases stay compatible while native changes create a boundary.
Channels Internal, production, and optional canary Keep promotion simple while preserving dogfood and gradual release paths.
Apply behavior Background download; apply on next cold launch Avoid interrupting live terminal and source-control work.
Production gate One protected-environment approval with Slack notification Matches the current release habit without coupling approval to KMS.
Rollout model Start with all-or-nothing plus instant rollback; add cohorts later Minimize the initial control-plane surface.
CDN Choose after measuring GCS/CDN versus Cloudflare path costs Bandwidth dominates infrastructure cost; protocol logic does not depend on CDN.
